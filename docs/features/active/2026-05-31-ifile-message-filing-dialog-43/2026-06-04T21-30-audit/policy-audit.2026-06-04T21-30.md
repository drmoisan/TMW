## POL-1 Re-evaluation (this artifact's sole change vs T21-02)

### Prior finding (T21-02)

POL-1 was recorded as a FAIL: "Repo-wide C# coverage is 21.99% lines / 8.01% branches for a language
(C#) with changed files this cycle; repo-wide below 80% is a FAIL trigger." policy-audit
blocking_count was 1.

### New ground-truth evidence

`evidence/qa-gates/2026-06-04T21-23/csharp-coverage-methodology.md` (orchestrator full-suite run;
the reviewer's local Bash is limited to `git diff` and cannot run the backend suite). Verified by
this reviewer against `.github/actions/dotnet-test/action.yml` and `git diff`:

1. **The "canonical" C# coverage artifact is a single project's file, not a merged repo-wide figure.**
   `.github/actions/dotnet-test/action.yml` runs `dotnet test ... --collect:"XPlat Code Coverage"`,
   which emits a separate `coverage.cobertura.xml` per test project. The next step selects ONE file:
   `Get-ChildItem TestResults -Recurse -Filter coverage.cobertura.xml | Sort-Object LastWriteTime
   -Descending | Select-Object -First 1` and copies it to `artifacts/csharp/coverage.xml`. There is
   no ReportGenerator merge. The "21.99%/22.79%" figure is the `TaskMaster.Api.Tests` project's
   single-file view, which loads but does not exercise the Application/Classifier/Infrastructure
   assemblies, so their lines inflate the denominator. (Verified directly: the action.yml step copies
   the single most-recently-written file; no merge step exists.)

2. **Full backend suite ground truth (orchestrator run):** `dotnet build TaskMaster.sln
   --warnaserror` clean; all 145 backend tests pass (ArchitectureTests 10, Schema 24, Application 43,
   Worker 4, PlaceholderGolden 1, Classifier 14, Infrastructure 21, Api 28). Eight per-project
   coverage files were emitted with line-rates ranging 0%–65%; no single file is a merged repo-wide
   figure. Application's 43 dedicated tests showing ~18% in another project's file is the signature of
   the single-file artifact, not real coverage of that package.

3. **Cycle 2 introduced zero C# production changes.** Verified via `git diff`: cycle-2 deliverables
   are TypeScript, manifests, package.json/lock, `.dependency-cruiser.cjs`, and docs. The only
   modified C# files (`src/TaskMaster.Api/Program.cs` OBO DI wiring; `TaskMaster.Api.csproj`
   whitespace) were already modified in the working tree at session start, BEFORE any iFile
   remediation (session-start git status: `M src/TaskMaster.Api/Program.cs`, `M
   src/TaskMaster.Api/TaskMaster.Api.csproj`). They are not cycle-1 or cycle-2 deliverables. The T21-02
   analysis found the changed `Program` class at 87% with no changed-line regression.

### Determination

POL-1 as written rests on two errors: (a) reading a single-project coverage file as a merged
repo-wide figure, and (b) attributing pre-existing, out-of-cycle working-tree C# edits to cycle 2.

- The coverage policy enforces "no regression on changed lines" plus the line/branch thresholds.
  Cycle 2 has **no C# changed lines**, so the "no regression on changed lines" obligation is trivially
  satisfied; there is no changed line that is uncovered.
- The one pre-existing C# edit's changed lines (`Program.cs` DI method-chain) are 87% covered with no
  regression. The csproj change is whitespace only.
- The low number is produced by the CI single-file-pick methodology applied to **unchanged** backend
  packages (Infrastructure/Application/Classifier). Blocking the iFile cycle on coverage of unchanged
  backend packages would also violate the "no broad refactors across unrelated projects" rule and this
  cycle's explicit out-of-scope boundary, which excludes the C# backend from cycle-2 change.

No genuine, cycle-2-attributable coverage regression exists after accounting for the methodology.
**POL-1 is downgraded from FAIL to Info/observation.** It is not a cycle-2 defect and is not a
blocking finding. No genuine coverage standard is weakened: the changed-line and threshold rules
remain in force; they are simply satisfied (no cycle-2 C# changed lines; pre-existing edit 87%
covered, no regression).

### Separate, pre-existing, out-of-scope follow-up (recorded, not blocking)

The CI canonical-coverage methodology — selecting one arbitrary project's file by LastWriteTime rather
than merging all per-project files with ReportGenerator — is a pre-existing reliability gap in the C#
coverage gate. It produces a number that cannot be interpreted as repo-wide and is the root cause of
the T21-02 misread. Recommended as a standalone follow-up (potential separate work item). It touches
`.github/actions/**`, so fixing it would itself trigger the `modified-workflow-needs-green-run` policy
rule and require a green workflow run against the branch head. It must NOT be folded into iFile cycle 2.
